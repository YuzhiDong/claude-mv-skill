# 手绘动画

一套**完全用代码画短片**的方法。提炼自 [JohnHeibel/PDoomVideo](https://github.com/JohnHeibel/PDoomVideo)（一支 156 秒、由 Claude Opus 画完的 MV）和它的通用版本 [ClaudeAnimationBase](https://github.com/JohnHeibel/ClaudeAnimationBase)（MIT），后者作为 `template/` 打包在这里。

**它怎么跑起来：** 每一帧都是时间 `t` 的纯函数。`studio.html` 加载 p5.js（只当画布与变换用）和你的场景文件；每个镜头把整张 1920×1080 的画面用**扁平色块 + 沸腾的墨线**画出来，绘制走原生 canvas 2D，没有笔刷、没有纸纹、没有颜料混合。`render.mjs` 驱动 headless Chrome：既可以渲染 contact sheet 供审片，也可以并行渲染每一帧；最后由 ffmpeg 编成 MP4（给了音频就一起混进去）。

## 工作流

**一条流水线，照顺序走，不跳步。** 全片只有**两个**确认点：**粗样片**（1.5）和**渲染授权**（5）。
其余自己定——包括三张设计表，那是给自己用的思考工具，不是呈给用户的公文。

| 步 | 动作 | 产出 | 等用户 |
|---|---|---|---|
| 0 | 起工程 + 把 `ANIMATION_GUIDE.md` 读完整 + 实测 BPM 与首拍偏移 | 工程目录、`src/config.js` | 否 |
| 0.3 | **节奏预算**：镜头切分按节拍不按句号，定短/中/长三档分布（短镜 ≥5、长镜 ≥2） | `STORYBOARD.md` 最前 | 否 |
| 0.4 | **歌词兑现表**：四种兑现方式任选，动作型 ≤60%，每镜 reads ≤3 | `STORYBOARD.md` | 否 |
| 0.5 | 场景表 + 色彩表 + 故事形状 + 构图骨架 | `STORYBOARD.md` | 否（自己用） |
| 1 | **分镜粗版**：每镜只写事件、reads 条数、一句构图意图——**不写秒级 reads、不写景别数值** | `STORYBOARD.md` | 否（除非用户要审） |
| 1.5 | **粗框架全片**：全部镜头搭出来，只求"存在、能读、接得上" | 全部 `src/scenes/*.js` + `out/draft.mp4` | **是**（框架过一遍） |
| 1.6 | **补细节**：构图、元素密度、表演、转场、色彩；**这时才把 reads 精确到秒、把景别写成数值** | 同上，逐镜改 | 否 |
| 2 | ~~只做前两镜~~ → 已并入 1.5/1.6（见下节「两段式」） | — | — |
| 3 | 一镜一镜磨到能出片 | `src/scenes/*.js` | 否 |
| 4 | 审片三段（代价递增，见下节）：**4a 静帧 → 4b 全片总结图 → 4c 动效预览** | `out/overview.jpg`、`out/animatic.mp4` | 4a/4b 否；**4c 前报数** |
| 5 | 出片 | `out/video.mp4` | **是**（先报帧数 + 耗时） |
| 6 | 核验（`ffprobe`）+ 压 720p 预览 | 交付物 | 否 |

**分镜为什么分粗细两版**：秒级 reads 只有在画面搭出来之后才写得准——站位、构图、动作时长全是搭的时候才知道。
框架之前把最贵的推演（逐秒安排）做在信息最少的时候，是成本倒挂，而且会让人误以为"分镜写这么细，照着做就行"。

### 两段式：先框架，再细节（用户 2026-11 明确要求）

> 原话："先定框架，再补细节，可以先给我一个不注重细节的粗糙的样片，画面有 bug 都没关系，
> 这个尽可能快地出，不要去抠细节，这个通过了再去完善细节。"

**这条优先于"前两镜钉死画风"那条。** 先把画风磨到完美、再往后铺，看起来稳，
实际上是把风险全押在前两镜的判断上——如果框架方向本身错了，磨得越细，废得越多。

| | 第一段：框架 | 第二段：细节 |
|---|---|---|
| 目标 | **16 镜全部存在、能读、接得上** | 好看、准、有层次 |
| 每镜花的时间 | 5–10 分钟，不回头 | 反复改，5–6 轮 |
| 允许的毛病 | 站位偏、比例怪、元素少、转场生硬、颜色不对 | 一个都不许 |
| 检查手段 | `--sheet` 28 帧总览 + `--animatic` 粗样片 | 4a 静帧 → 4b 总览 → 4c 动效 |
| 交付 | `out/draft.mp4`（6fps 带原曲） | `out/video.mp4` |
| 用户确认点 | **是**（走向、节奏、每句歌词有没有兑现） | 否（除非要审） |

框架阶段唯一的验收标准：**用户的每一条意见都能对应到"哪一镜、第几秒"**。
所以草稿必须带音乐、时间码可查——没有时间码的草稿，用户只能说"整体感觉不对"，
那种反馈没法改。

**确认之后不要再打断。** 除了这三种情况——素材缺失、歌词与音频长度对不上、渲染连续失败两次——
一路做到交付再说话。中途的取舍（转场用哪种、某镜加不加道具）自己定，写进交付说明，**不要每做一镜问一次**。

### 0. 起工程

```bash
bash ~/.claude/skills/painted-animation/scripts/new_project.sh <项目目录>        # 加 --keep-demo 保留示例场景
```

这一步会复制模板、摘掉示例场景、跑 `npm install`，并检查 node / ffmpeg / Chrome。然后**把 `<项目目录>/ANIMATION_GUIDE.md` 整份读完**再动手设计——里面是规则、动画原理，以及完整的引擎 / Clawd API。用 Read 工具看一眼 `docs/emotions.jpg` 和 `docs/views.jpg`（角色表情表和视角表）。

如果是 MV，或者片子超过 20 秒左右，再读一遍 [references/music-video.md](references/music-video.md)。

**每支 MV 在写分镜或写代码之前，先把这几件事问完：**

1. 请用户同时提供歌曲音频和它的 `.lrc` 歌词文件。需要 LRC 的时候，不要编造、不要用转写、不要凭听感补词。
2. 创意方向一定要问，哪怕用户已经说了一部分。**用一条自然语言问题、一条消息问完**，覆盖想要的故事和整体感觉，以及希望反复出现的意象或不想要的内容。不要拆成多个问题、多个字段、清单或五段式表格。告诉用户一句话作答即可，也可以留空。示例："这支 MV 你想要什么样的故事和整体感觉？有没有希望反复出现的画面，或者想避开的东西？没想法可以留空。"
3. 确认收到的文件，并把从这句回答里推断出的创意方向复述一遍。内部自行提取故事、情绪、气氛/意象、视觉母题、要避开的内容；**不要**反过来让用户按这五类分别作答。留空视为"没有偏好"，不是漏填，在分镜阶段给出一个合适的解释即可。音频或 LRC 缺失时，暂停 MV 流程并明确索要。
4. 用 `scripts/beat_grid.py` 实测速度。歌词行通常比听上去快。以用户给的音频和 LRC 作为时间的唯一依据。

### 0.5 先设计世界，再设计镜头

**顺序：节奏预算 → 歌词兑现表 → 场景表 → 色彩表。** 先想"在哪儿"是本末倒置——地点是结果，不是起点。

**规则打架时，先看 [design-first.md](references/design-first.md) 开头那张裁决表（C1–C6）：**
节奏 > 歌词语义；引擎能力 > 审美愿望；全片明度基线 > 单段色相偏好；兑现配额 > 每句都兑现；
符号链完整 > 场景数量；极特写 / 极远景 > 元素密度指标。**没有这张表，规则越多越互相抵消**——
"宁可少换一个景保符号链"和"一段必须换一处空间"就足以让同一个问题两次给出不同答案。

**先排节奏，再排画面。** 镜头在哪切由**节拍**定，不由"这句唱完了"定：一行歌词可以配 1 个镜头、3 个镜头，
或者两个镜头共用一行。56 秒的片子至少 **5 个短镜**（0.5–1.2s）和 **2 个长镜**（5–8s）。
全都落在 2.6–3.8 秒，观众说不出哪里不对，只会觉得"平"——因为长镜头的静和短镜头的切都被锁死了。

**然后是歌词兑现表，四种方式任选：**

| 方式 | 手段 | 例 |
|---|---|---|
| 动作型 | 造一个能被手碰到的实物，让角色对它施力 | 灰幕被五指抓住往下扯 |
| 尺度型 | 极远 ↔ 极近的跳变 | 瞳孔里的海 → 拉出成真实海面 |
| 时间型 | 停顿、定格、慢到不像在动 | 烟花停在空中，只有头发和海浪还在动 |
| 重复型 | 同一动作换人换结果 | 他撕一道、她撕第二道 |

**动作型的占比压在 60% 以内。** 它是四者里最"说明性"的一种，全片六成都在"抓一个东西、塞一个东西、
撕一个东西"，片子就变成流程演示了。三问答（动词是什么 / 承受动作的东西长什么样 / 做完哪里变了）
只用来检验动作型；答不上来的典型症状是**用氛围代替动作**——"拨开阴霾"画成擦窗户，
"收集快乐"画成一面照片墙，气氛同类但歌词要的那件事没发生。

**每镜 reads 不超过 3 条，超过就拆镜。** reads 是观众依次必须看懂的东西：2.97 秒里塞 5 条，
等于 0.59 秒一条，写的时候觉得排得下，渲出来必然糊。

然后才是**场景表**（地点 / 前景·中景·远景 / 镜头运动）和**色彩表**（主色 + 光源实体）。
全片只用一个地方，无论分镜多好都会读成"没做完"；每个地点挑一个**不同的构图骨架**。
**换景不等于换地点**：七个场景全用中景平视，观众看到的是同一张明信片换了七张底图——
尺度、空间逻辑（分屏 / 从眼睛里看出去 / 幕布被撕开）、视点高度、载体，每段至少动两种。

**元素密度按段给，不按镜给**：每段累计 6–8 件可辨物件、≥2 件前景、≥1 件会动、≥1 个建立镜头
（`zoom` 0.74–0.92）。`zoom ≥ 1.6` 的极特写和 `≤ 0.72` 的极远景**豁免**——一只眼睛的特写里
没有六件物件，这不是缺陷。逐镜套指标只会逼着每个镜头都塞满。

**明度由歌定，不由题材定。** 欢快的歌做成灰暗夜戏，是美术习惯压过了歌的要求。轻快的歌主色明度 65–85%、
饱和 45–70%；每一段压暗都要能引用一句歌词，引不出来就是手在习惯性变暗。

完整模板、裁决表、四种兑现方式、六种骨架、自检命令：[references/design-first.md](references/design-first.md)。

### 1. 先写分镜（粗版）

在工程里写 `STORYBOARD.md`。前半段是设计表（节奏预算、兑现表、场景表、色彩表、母题、情绪弧线），
后半段是逐镜。

**逐镜只写五个字段，够搭就行：**

| 字段 | 要求 |
|---|---|
| 标题行 | `镜号 · 场景名 ｜ 起止秒 ｜ 对应第几行歌词` |
| 事件 | 谁做了什么、因→果、画面哪里变了。**必填** |
| reads | 只写**几条**、分别是什么，**不写秒** |
| 构图意图 | 一句话（"贴地仰拍，灯在左上一角"） |
| 转场 | 进和出的方式 |

**其余字段留到 1.6 阶段补**：reads 的精确秒数、`zoom` 数值、"这一镜最容易错的地方"。
画面没搭出来之前，这些数值都是猜的。

可参考的完整例子：[examples/xiaozhen/](examples/xiaozhen/)（一支 31 秒的歌词视频，分镜和全部场景代码都在里面）。

做 MV 时，把用户的故事和情绪转成一条连贯的视觉叙事和情绪曲线。

**"不逐句插图"不等于"不用逐句兑现"——这两件事经常被混为一谈，混了就会出上面那种片。**
插图是"歌词提到海就画一片海、提到眼泪就画一滴泪"，词与画一对一直译、没有叙事。
兑现是"这一句说的那件事，在画面里真的发生了"——它可以是隐喻、可以换人换物，但**动词必须在**。
判断标准：唱完这一句，画面里有没有多一样、少一样、变一样？没有，就是没兑现。
（例外：纯情绪的过渡句，全片最多 2 行可以不兑现，但必须紧邻一个强兑现行，且写明理由。）

### 2. 一镜一镜地搭

- 在 `src/config.js` 里设 `duration`、`bpm`、`offset`（以及 `audio`）。
- `src/scenes/` 里一个场景/章节一个文件，用 IIFE 包起来，结尾写 `shots([[t0, fn], ...])`；再到 `studio.html` 里加上它的 `<script>`。
- **先摆关键姿势**，用静帧检查它们，再补中间的动。
- **先全片搭一遍粗框架（1.5），再回头磨（1.6）。** 框架阶段每一镜只花 5–10 分钟，
  只要"存在、能读、接得上"；站位偏、比例怪、元素少、转场生硬都放过。
  框架被用户认可之后，画风和构图才有意义——**如果框架方向本身错了，前两镜磨得越细，废得越多。**
- 磨细节阶段才用"前两镜改 5–6 轮"那套：背景底色、雨的密度、角色对比度、相机构图在那一轮定下来，
  后面十几镜照同一套参数铺。反过来做——先铺 15 镜再统一调——就是全线返工。

### 3. 渲染出来看——每个镜头，看几遍

光读代码是看不见运动的。在工程目录下：

```bash
node render.mjs --sheet=0.1,0.8,1.6,2.4 --cols=4 --w=480 --out=out/check/a.jpg        # 关键帧
node render.mjs --strip=2.1:2.6 --out=out/check/strip.jpg                             # 某一小段的每一帧
node render.mjs --sheet=2.3 --crop=760,420,500,400 --w=500 --out=out/check/face.jpg   # 全分辨率细节
```

用 Read 打开每一张，照着指南里的检查清单逐条过：事件清楚吗？角色够大吗？reads 的时间够第一次看的人看懂吗？有预备动作和跟随动作吗、有没有突然跳变？脚和手持道具接触上了吗？每个接缝都有转场吗？有没有出现文字、3D、纯黑纯白、发浑的光晕？改完再看一遍。**预算是：每个镜头至少一张 sheet，每个关键动作和转场一条 strip，每张承担叙事的脸一张 crop。**

contact sheet、静帧、短 strip 这类几帧的预览，可以直接在当前环境里渲染和审看。刻意做小、做准；它们是用来验证画面的，不能代替整片渲染。

### 4. 出片

出片之前不要直接开整片渲染。预览审完之后，告诉用户整片云端渲染很慢，并明确问他要本地渲还是云端渲。等他回答；"分镜通过了""预览通过了"或者之前说过"继续"都不等于渲染授权。

- 用户选本地：就不要在云端跑整片。除非他后来明确改口。把验证好的工程文件准备好，如果不清楚他的系统就问，然后给出对应平台的确切前置条件、`npm install`、逐帧渲染和编码命令。保留预览图，让他知道自己批准的是哪一版。
- 用户选云端：先确认预计时长、帧数和大概的时间/成本，再跑可续跑的多线程渲染。
- 用户没回答或答得含糊：不要渲。再问一次，要一个明确的本地/云端选择。

**本机也一样要问。** "跑在同一台电脑上"只说明不用讨论云端，**不等于可以直接开跑**。整片渲染（`--frames` / `--clip`）开始前，必须先报「帧数 + 预计耗时 + 这会覆盖哪一版」，拿到用户明确的同意再启动。未经同意就开跑属于严重违规——用户可能正在改别的东西，或者根本还没决定要哪一版。

只有几帧的预览渲染（`--sheet` / `--strip` / `--crop`，通常 ≤ 20 帧）不受此限：那是审片用的，不是产出。

### 出片之前的三段审片，一段比一段贵

正式渲染跑一次就是几十分钟，**所有能提前看出来的问题都要在这三段里看出来**。按代价从低到高：

| 段 | 命令 | 能看出什么 | 代价 |
|---|---|---|---|
| **4a 静帧** | `--sheet` / `--strip` / `--crop` | 单镜的构图、表情、道具、接缝 | 每帧 0.3–0.9 s |
| **4b 全片总结图** | `--sheet=1,3,5,…,55 --cols=4 --w=480` | 全片结构、场景有没有真的换、色彩弧线有没有拉开 | 28 帧 / 约 15 秒 / 一张图 |
| **4c 动效预览** | `node render.mjs --animatic --step=4` | 节奏、转场、动作连贯、字幕与唱词的咬合 | 约 1 分钟 / 338 帧 / 20 MB |

**4b 是这套引擎里最被低估的一步。** 把整片按固定间隔抽帧、拼成一张带时间码的图，一眼就能看出"是不是一个地点讲到尾""背景是不是一片同一个颜色""六处场景是不是同一个构图骨架"——**这三个问题只有把它铺成一张图才看得出来，单镜怎么看都看不出来。**

间隔按片子长度定：2 秒一帧最通用（56 秒的片子 = 28 帧，4 列 7 行，15 秒渲完）。片长超过 3 分钟就放到 4 秒一帧，别让单格小到看不清。

时间码由 `renderSheet` 自动叠在左上角（黑底白字，字号跟着图宽走），**不用另外加字幕条**。

**4c 必须带原曲。** 不带音频的 animatic 看不出"动作有没有卡在拍子上"，而那恰恰是最容易出问题的地方。默认 `--step=4`（6 fps）：动作会略卡，但节奏和转场看得准；要更连续用 `--step=2`（12 fps，代价翻倍）。

顺序不能反：**4b 通过之后再花 1 分钟跑 4c，4c 通过之后再申请正式渲染。** 反过来（先渲全片再看）就是整片返工——这件事真的发生过。

## 最重要的几条规则

以下是指南里规则的浓缩版，以指南为准。

1. **媒介是硬的：色块、描边、沸腾。** 只用 `paint()` / `inkLine()`（canvas 2D 填充与描边）——绝不用 p5 原生的 `rect`/`ellipse`/`fill`。纯平面 2D：转身靠画出来的关键视角（`turn()`、`spinView()`），绝不做 3D 投影。颜色是**不透明覆盖**，没有颜料混色，黄压蓝还是黄，所以层级关系全靠绘制顺序和 `washOp` 控制；光只能用 `glow()`（叠加）。
2. **不要文字。** 没有字幕、标签、招牌、对话气泡；用画面表达。角色的反应是画出来的符号（`!`、汗滴、爱心……）。唯一的例外是歌词视频里的卡拉OK，以及最多几个大的拟声字。
3. **每个镜头里都要有事发生**——一个事件、因→果、埋下的伏笔要兑现。
4. **给观众时间。** 把每个镜头的 reads 列出来；一次只给一个；动作要快，含义要停；先引导视线；**reads 决定镜头长度**——**一镜最多 3 条，超过就拆镜**（2.97 秒塞 5 条 = 0.59 秒一条，等于没给时间）。这是 AI 生成动画最容易翻车的地方。
5. **活着。** 没有东西是静止的（`feel()` 的待机动作、漂移的相机、沸腾的线条）；表情变化走 `emotions()`，绝不手动切换；角色要够大（中景 u≈20–28，特写 40–70）；一切都踩在节拍上。
6. **每个接缝都要转场**，并且挑符合故事的（笔刷擦除、圆形/异形光圈、甩镜、匹配剪辑、动作接、相机带走）。
7. **它是一件作品。** 一个世界、一条色彩弧线、一条情绪线、场景之间互相勾连、结尾与开头押韵。

## 引擎的坑

这一版是**纯平面 canvas 2D**（不再依赖 p5.brush）。下面每一条都是改造时踩出来的。

- **自定义颜色的角色，`emotions()` 必须传 `base`，否则换表情时角色会变回默认赭色。**
  `emotions()` 做表情过渡时会把颜色算死写进结果——它不知道你的角色是什么颜色，就退回 `PAL.clay`。
  粉色 Clawd 一切表情就变橙，过渡瞬间还会橙粉闪烁。正确做法是给每个角色包一层
  `cast.js`，表情永远走带 base 的包装：`const lanMood = (t, keys) => emotions(t, keys, { base: CAST.lan })`，
  场景里写 `lan(x, y, u, { ...lanMood(t, keys), view: 'q' })`。**不要**直接 `emotions(t, keys)` 再 spread 给
  `lan()`——spread 顺序会让 emotion 算出的颜色盖掉角色的粉色。
- **挂在角色身上的东西（围巾、背包、挂牌），位置一律读 `CLAWD_ANCHORS`，不许手写 y。**
  Clawd 的身体是 -8u（头顶）到 -2u（下巴）的方块，`-7.5u` 在代码里看着像"脖子"，画出来在头顶上。
  手写魔法数字这类错只有渲出来才看得见。引擎每个角色都会在 `?anchors`（`render.mjs --anchors`）时把
  锚点全部画成红线标注——**写完挂件先渲一帧 `--anchors` 对一眼**，几秒钟的事，比渲完成片再返工便宜得多。
- **2D 画布的原点在左上角，WEBGL 在中心——这一条会毁掉整张画面。** 从水彩版迁过来时，`draw()` 里有一句
  `translate(-W / 2, -H / 2)` 是为了把 WEBGL 的中心原点掰回左上角；换成 2D 后必须删掉，否则所有内容整体
  偏移半张画布。同理 `flushLetters()` 里的 `resetMatrix(); translate(-W/2,-H/2)` 也要去掉补偿。
- **`wash` 是颜色本身，`fill` 只是第二层。** 平面版只认 `wash` 画实体色块；只写了 `fill` 没有 `wash`
  的形状（反光、水洼、光斑、柔光）会降级成同色的半透明色块。**要一个物体有明暗，就叠两层不同 `washOp`
  的同色系，或者给它一个 `fill` 层**。不要再写 `bleed` / `tex` / `border`——那三个参数现在完全无效。
- **`INK_W`（=3.2）是线宽系数，`sw=1` 约等于 3.2 像素。** 全景镜头里 `sw` 1–2 合适；特写里要压到
  0.4 以下，否则一根轮廓线就占满画面。描边是等宽的 `stroke()`，没有水彩的锥形收笔——需要粗细变化时，
  用两段不同 `sw` 的线叠加。
- **`flushBrush()` 现在是空函数**（保留只为兼容旧代码）。绘制立即生效，所以"glow 必须画在 paint 之后"
  这条不再成立；但**绘制的先后仍然决定遮挡**，光画晚了会盖住主体。
- **`karaoke.js` 必须在 `studio.html` 里挂上**，而且要排在 `timeline.js` 之后。模板一度漏了这一行，
  结果整片字幕凭空消失，查了很久。
- **帧是 `t` 的纯函数。** 帧并行、乱序渲染：不能有跨帧状态、不能用 `Math.random()`、不能逐帧积分物理。
  稳定随机用 `hash(i)`，沸腾用 `jit()`。
- **`boilSeed(key)`** 要在每个独立的背景元素/道具前调用，否则一个会动的东西会让它之后画的所有东西每帧重新抖。
- **别用 p5 的全局名命名。** p5 把 `line`、`OVERLAY`、`text`、`color`、`scale` 等都定义成了全局；顶层写
  `function line()` 会报 `Cannot redefine property`，页面永远进不了 ready（渲染器超时）。辅助函数放进场景的
  IIFE 里，或者换个不撞的名字。
- **scene 里定义 `const DUR` 会和 core.js 的全局常量撞车**（`Identifier has already been declared`），
  整页白屏。要用就换个名字（`TOTAL`）。
- **雨、雪、粒子要画在人物之前**，否则雨丝会穿过脸。但在"人在雨里被淋"的镜头里，雨又该有一薄层压在人物
  前面——两层分开画：一层在人物后（密的），一层在人物前（稀的、更淡的）。
- **覆盖式转场不能盖住脸**：遮罩、擦除、落下的布，底边留在人物头顶以上；要盖满整个画面时就明确"这是幕落"，
  别停在半截。
- **拉走、揭走这类动作必须有可抓的东西**：垂下的带子、握住的柄，手正好落在上面，否则就是在抓空气。
- **门洞、窗、屏幕里的分层：** 先画里面的东西，再把周围的墙/框画回来盖住，这样比洞口宽的东西才不会露到外面。
- 点表里出现 `NaN` 会抛 `Failed to construct 'OffscreenCanvas'`——退化几何要先挡掉。
- macOS：渲染器会用 `--use-angle=metal`，并自动找 `/Applications/Google Chrome.app`；否则传 `--chrome=<路径>`。

## 性能参考（M 系 Mac 实测，1920×1080 / canvas 2D）

- **单帧 1–20 ms**（多数 2–5 ms）。一帧的成本只跟路径数量有关，跟像素数几乎无关。
- **28 帧总结图：2.7 秒**（含启动浏览器）。改之前同样的图要 15 秒。
- 全片 1350 帧约 **20–40 秒**（瓶颈已经变成截图和写盘，不是绘制）。
- 6 路并发仍然是甜点，但它不再是瓶颈；`--workers=4` 足够。
- 渲染器默认 **24fps**（不是 30）。写文档、报时长之前先看 `render.mjs` 顶部。
- **增量渲染靠镜头注册时记下的来源文件**：`shots([[t0, fn, 's09']])` 第三个参数是镜号（不写就用索引）。
  `--frames` 会比对 `out/manifest.json` 里的源码 mtime——只有某个 `sX.js` 变了就只重渲它注册的镜头；
  `_shared.js` / `core.js` / `clawd.js` / `config.js` / `karaoke.js` / `timeline.js` 任何一个变了就全片。
  改完一镜先 `--dry-run` 看它打算渲哪些，别手算帧号。
- **局部改一镜**：删掉对应帧号，再 `--range=a:b` 重渲，最后 `--encode` 全片重编（约 1.5 分钟）。
  **删帧范围和重渲范围必须对齐**（帧号 = `round(t × fps)`），差一帧序列就断，ffmpeg 会**静默截断**成片。
  出片前一定要 `ffprobe` 核 `duration` 和帧数，不要只看那句 `wrote out/video.mp4`。

## 中文歌词、字体与时间轴

- **有现成的时间轴就直接用。** 工程里已经有的逐行或逐字时间（`content/lyric-timing.json`、LRC、SRT）是**冻结产物**——拿来用，不要重算。用"保险起见"重跑人声分离，等于把整件事里最贵的一步白烧掉。
- **绝不用 ASR 猜中文唱词。** whisper 系模型对中文演唱不可靠，屏幕上错一个字比不写字更糟。文字来自用户、LRC 或歌词站；时间来自已有文件。
- **`karaoke.js` 已经处理了 CJK。** `KFONT` 是 `"Ma Shan Zheng", "Kaiti SC", "STKaiti", serif`——毛笔字体走 Google Fonts，加载不到就回落到系统楷体，所以在墙内也能渲出来。整片渲染之前，先渲一帧带字的看一眼。
- **`beat_grid.py` 会打两个 BPM。** 快脉冲和半拍（例如 143.55 和 70.30）。抒情慢歌取**小的那个**，否则所有待机和弹跳都会显得慌。

## 改造成自己的

- **调色板就是美术风格。** 全套颜色在 `PAL`（`src/core.js` 顶部）和每个场景文件里的十六进制之间。
  想让整片换一种气质，改 `PAL` 里那十几个值比改任何代码都有效——色块动画的"味道"有八成来自配色。
- **明暗只有两三层。** 一个物体 = 底色 + 一个暗部 + 也许一个高光，全用同色系的不同明度。三层以上就开始
  像水彩，那正是这一版去掉的东西。
- **线条粗细是 `sw × 3.2`。** 全景 `sw` 1–2，特写 0.3–0.6。整片保持同一个系数，线条才像同一个人画的。
- Clawd 是默认主角，不是必须。新角色、道具、情绪都用同一套工具画（`paint`、`ribbon`、`through`、`glow`），并且在每个镜头里保持同一套型；新情绪加在 `src/clawd.js` 的 `EMO` 里。
- `src/karaoke.js`（模板自带）通过 `core.js` 里的 `window.overlayHook` 钩子，给歌词视频做逐字卡拉OK。
- `LOOPS.name = t => {...}; LOOPS.name.len = 4;` + `node render.mjs --loop=name --png` 可以做一个无缝循环，用来出 GIF（`ffmpeg -i out/loop_name/f%04d.png …`）。
- 推理强度调高，场景通常会画得更铺张、更细。
